| TD-41 | `geometry/internal/KernelUtil.h`, `geometry/Modeling.cpp` | Access violations inside OpenCASCADE are turned into failures through OCCT's signal handlers and a `longjmp` (`OCC_CONVERT_SIGNALS`; `OSD::SetSignal` once, and OCCT's C signal handlers are active only while a kernel call runs (`KernelSignalScope`, counted across threads): outside kernel calls OCCT's handlers would turn every crash into `exit(1)`, hiding it from the crash log and the OS crash reporter; `--simulate-kernel-fault` and the recovery scenario check both sides). Objects between the crash and the catch point are not destroyed (leaks), OCCT's state after such a jump is not guaranteed, and it relies on the C runtime's `signal(SIGSEGV)` path: an application crash handler installed with `SetUnhandledExceptionFilter` must chain to the previous filter, or kernel crashes end the process again. Worker threads (TD-1): the kernel lock is taken before the handlers are installed, so they are installed and removed by the thread that runs kernel code (the Windows C runtime keeps SIGSEGV handlers per thread); a fault on the preview worker comes back as a failure (`KernelThreads.FaultOnAWorkerThreadBecomesAFailure`). On POSIX (macOS, iPad) `sigaction` handlers belong to the whole process, so kernel calls install a dispatcher (`onKernelSignal` in `Modeling.cpp`) that hands a fault to OCCT's handler only on the thread in the kernel call (the kernel lock owner) and to the handler from before (the crash log) on any other: a GUI-thread crash while the worker computes a preview is still logged and reported instead of ending in OCCT's `exit(1)` (`KernelThreads.FaultOnAnotherThreadDuringAKernelCallIsNotTheKernels`; only CI's macOS job runs that path). On Windows OCCT's own C signal handler locks a process-wide mutex and jumps back with it still locked: after a fault on the preview worker, the next fault on the GUI thread (e.g. applying the step whose preview crashed) waited forever - a frozen app. Kernel calls on Windows therefore install our own handler (`onKernelSignal`), which raises the same OCCT exception without the mutex (`KernelThreads.FaultsOnTwoThreadsInTurnAreAllContained`). OCCT's top-level exception filter (which `CrashLog` chains to inside kernel calls) still takes that mutex; it is only reached by a fault on a thread without our handler that is inside an OCCT try block (OCCT's own thread pools, if a parallel algorithm crashes there). The crash itself reads garbage memory, so whether it happens varies from run to run (a stress seed failed once in a long run and passed alone). | Found 2026-09-25 by the stress test: a General Fuse (mirror of a filleted two-piece body) crashed in OCCT's solid classifier; a failed step with a message beats losing the session. | Report the OCCT bug upstream with `tests/data/fuse-crash-fillet-corners.brep`; re-test with OCCT 8 (TD-10). |
